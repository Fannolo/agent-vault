# Read-only cross-judge: production browser architecture

Reviewed 15 October 2026 against `grounding.md`, both candidates' prose and sketches, B's scratch probe record, the repo's `AGENTS.md`, and the architect red flags. This is an architectural comparison, not installed-system proof or a security certification. No candidate code was built or run by this judge; the working tree was not edited.

## Decision

**Use candidate B as the implementation base, with the amendments below. Keep production browser enrollment disabled until the installed gates pass.** B places the web host and Chromium under `_agentvaultweb`, distinct from both the shell-capable agent UID and the `_agentvault` broker, and makes the broker the sole owner of run authority. Its headless pipe, request-gate, frame and synthetic MFA prototype is useful evidence, while `proto/RESULTS.md` accurately says it used `--no-sandbox` under `sandbox-exec` in an interactive session. It is **not** P0 proof of a sandboxed LaunchDaemon under a private UID. The planned P0 test must check the renderer sandbox actually engages, not infer that merely from absence of `--no-sandbox` in `ps`.

Candidate A has a valuable no-NIC egress idea and a stronger challenge-only input specification, but its central process map is internally inconsistent: `RATIONALE.md` calls BrowserHost a dedicated-UID component, while `DEPLOYMENT-AND-PROOF.md` says the `_agentvault` Broker starts BrowserHost as a child **under the same private UID**. That exposes the broker's Keychain-owner UID to a browser-host or guest/host escape, contrary to its claimed compartmentalization. It also adds a custom Linux image, QEMU, tunnel relay, guest worker, Chromium and their release/update pipeline without a working appliance or measured startup and challenge behavior. It should not be selected on paper strength alone.

## Graft into B, without a second browser backend

1. **A's frame/input binding:** add challenge epoch and latest-frame ID to the continuation lease and every input batch. Before capture and before each input, verify the current run phase, main-frame/iframe origin and exact reviewed challenge path; expose only a challenge-specific crop or fail closed when one cannot be established. Revalidate after every navigation and on broker return. Bind the lease to the authenticated XPC connection or an equivalently verified connection identity, not PID alone; handle reconnect with a new signed open. Keep event coordinates, text length, event count, time and rate bounded. This is a change to B's one host path, not another UI stack.
2. **A's late-reply/priority invariants:** record run and host epochs, reject stale host replies after revoke/cancel/rotation, and ensure a start racing teardown ends the newly created host run. Prioritize destroy/control over frame traffic. Test revoke during credential load, host start, frame wait and classification; preserve the last allowed call's collectability.
3. **A's egress objective, adapted to B:** define a separately enforceable network boundary for the `_agentvaultweb` process tree, with a finite compiled destination set and verified behavior for redirects, service workers, WebSockets, WebTransport/QUIC, DNS, prefetch and Chromium background traffic. The in-browser phase/path gate remains necessary for page behavior. Do not copy the QEMU tunnel implementation unless native enforcement cannot be proved and the whole deployment is reconsidered as one coherent backend.

## Red flags and required proof

- **P0 is blocking.** B's `sandbox-exec` probe deliberately disabled Chromium's own sandbox. An installed, Bite-signed `_agentvaultweb` LaunchDaemon must demonstrate rendering and frame/input before login, during login and across fast user switching, with Chromium's sandbox positively verified. A signed review bundle, same-UID fixture or process argument check is insufficient.
- **P1 is blocking.** From the agent UID, verify profile/cookie directory denial, host Mach-service denial, process attach/task-port denial, no reachable CDP listener, and absence of interference with the user's installed Chrome and other app profiles. B's scratch proof of no cookie bytes on disk is narrow; do not equate it with a general storage or isolation guarantee.
- **P2/P3 are blocking.** Installed app/user-presence opening and bounded challenge continuation must work; revocation, account rotation/deletion, client loss, expiry and broker/host death must tear down sessions and suppress late output. Demonstrate that frame load cannot starve admin revocation.
- **Network policy is blocking.** B currently treats CDP interception and URL blocking as the egress boundary. Verify process-tree egress independently of CDP; if it cannot be constrained to reviewed destinations, do not enable the service. A's no-NIC approach is an alternative architecture, not a drop-in patch.
- **Real-service compatibility is open.** GitHub login/profile selectors, required assets/challenge origins and headless acceptance have not been demonstrated with a designated test account. Review and pin exactly one service workflow. Do not widen origins merely to make a fixture or transient challenge pass.
- **Public API/maintenance:** derive Bridge/Wire/Core statuses from one enum and validate exact wire shapes. Keep WebHost credential-bearing DTOs private to the daemon/host link: B's sketch imports `AgentVaultWebHostProtocol` directly into Core although Core only needs a small `WebHost` port and fixed workflow/result domain types. Split that vocabulary or constrain imports so a future caller cannot accidentally gain the secret-bearing command type. Delete `SessionServiceAdapter` and the old WebKit production library after parity tests; no runtime fallback switch.
- **Proof scope:** Bite Developer ID identity `3JWAQ92CB4`, hardened-runtime entitlements, notarization, installer ownership and native protected-key signing remain separate measured gates. No changes here establish them.

The first implementation unit should be B's U0 run-state and contract reconciliation with a scripted host; incorporate the challenge-epoch and late-reply contract now so later units do not have to reinterpret run IDs. Then implement one host backend, synthetic integrated fixture, installed isolation/egress proofs, and finally the reviewed real-service gate. If native P0 or network confinement fails, revisit the whole backend choice and fix A's UID topology before building its appliance.
